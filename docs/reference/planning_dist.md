# `nimblecas.planning_dist` — Reference

**Author:** Olumuyiwa Oluwasanmi

Source: `src/planning_dist/planning_dist.cppm`

Distributed classical automated planning formulated over [`nimblecas.taskdag`](taskdag.md)
task graphs. While [`nimblecas.planning`](planning.md) executes heuristic search in a single
process, this module translates heuristic search problems into explicit task graphs that execute
under any conforming `Executor`: `serial_executor`, `local_parallel_executor`, or cluster-wide
`SgeeDistributedExecutor` over an SGEE broker.

The module is governed by a strict **honesty boundary** (Code Policy Rule 32):

- **What is parallel and what is not:** heuristic state-space search is not embarrassingly
  parallel, and the module does not pretend otherwise. The open list constitutes a sequential
  dependency: the determination of which state to expand next depends on the outcomes of every
  expansion preceding it. What is data-parallel is the computationally intensive component —
  evaluating the successors. In classical planning, evaluating a delete-relaxation heuristic
  requires solving a relaxed planning task for every generated state; on non-trivial problems,
  these evaluations dominate total search time. The module therefore enforces a clean
  decomposition:
  - The **coordinator** retains exclusive ownership of the open and closed lists, managing the
    search frontiers and deciding which states to expand.
  - The **workers** expand and evaluate candidate states and hold no search state between rounds.
  A worker receives the task definition and a batch of states, generates applicable transitions,
  evaluates each successor state under the chosen heuristic, and returns the resulting records.
  Because workers remain stateless across rounds, each expansion round is an ordinary task graph
  with no inter-worker communication.
- **Parallel expansion of an $f$-layer preserves optimality:** `distributed_astar_plan` expands,
  in each round, every open state sharing the minimum evaluation cost $f$. A* requires only that
  states be expanded in non-decreasing order of $f$; it does not impose any ordering constraints
  on states within the same $f$-layer. Expanding an entire $f$-layer simultaneously is therefore a
  valid A* expansion order, and the plan produced is guaranteed to be optimal for the identical
  reason that a serial A* plan is optimal.
- **No speedup is claimed:** evaluating an entire layer concurrently allows workers to process
  batches in parallel. However, an $f$-layer may contain a single state or ten thousand states, so
  any performance benefit depends entirely on the topology of the problem's state space and is
  not claimed in advance.
- **The equivalence contract, stated exactly:** `distributed_astar_plan` returns a plan of the
  **same cost** as serial `astar_plan`, always. It does **not** promise the identical sequence of
  steps. Serial `astar_plan` breaks ties toward the state discovered earlier in the serial traversal,
  whereas a parallel layer possesses no such temporal order. When a task admits multiple optimal
  plans of equal cost, the serial and distributed algorithms may select different paths — both
  optimal and both valid. Within `nimblecas.planning_dist`, the choice is strictly deterministic:
  successors merge in shard-index order followed by batch order, with ties broken toward the lower
  operator index. Consequently, the same executor and task yield the identical plan on every run,
  regardless of shard count or worker count.
- **Satisficing search bounds:** `distributed_gbfs_plan` provides distributed greedy best-first
  search and makes **no claim of optimality** regarding plan length or plan cost, exactly matching
  the contract of serial `gbfs_plan`.
- **Mandatory plan replay and verification:** planning is PSPACE-complete, and distributed
  execution does not alter that complexity. Every plan generated by `distributed_astar_plan` or
  `distributed_gbfs_plan` is replayed and verified from the initial state using
  `nimblecas::planning::validate_plan` before being returned to the caller. A plan that fails to
  reach the goal or that applies an invalid transition is treated as an error and is never returned.
- **Separation of unsolvability proof from resource exhaustion:**
  - `MathError::undefined_value` indicates that the reachable state space was completely exhausted
    without discovering a goal state. This is an exact proof that no plan exists.
  - `MathError::not_converged` indicates that the expansion budget (`max_expansions`) was exhausted
    while open states remained. This does not prove unsolvability; it indicates that the budget was
    insufficient.
  These two outcomes convey fundamentally different information and are distinguished by their error
  codes.
- **Cluster verification seam:** the equivalence contract is asserted across the
  `SgeeDistributedExecutor` in tests, confirming that task definitions and state batches undergo
  `Payload` encoding, transport through a broker queue, and remote registry lookups. However, the
  underlying transport in those test suites is an in-process broker (`FakeBrokerPort` with
  `InMemoryResultChannel`), not a physical network. What is verified is the executor protocol,
  the binary wire format, and the registry dispatch contract, not the behaviour of a physical
  cluster under network latency or network partition.
- **Structural layer bounds:** `max_layer_states = 1U << 20U` ($1{,}048{,}576$ states). Because a
  round materialises the states of a layer into task payloads, this cap prevents unbounded memory
  consumption from displacing search execution.

## Wire format and registered operations

Workers communicate with the coordinator via binary payloads using little-endian fixed-width
integers. Signed 64-bit integers travel using their two's-complement bit representation, ensuring
values round-trip without bit loss. Payload decoders validate element counts against remaining
byte lengths before allocating memory, rejecting truncated or corrupt payloads with
`MathError::syntax_error`.

```cpp
enum class Heuristic : std::uint8_t {
    h_max,  // ADMISSIBLE -- the only one distributed_astar_plan accepts
    h_add,  // inadmissible
    h_ff,   // inadmissible, and carries preferred operators
};

inline constexpr std::string_view expand_op_id = "nimblecas.planning.expand_shard/v1";
inline constexpr std::string_view evaluate_op_id = "nimblecas.planning.evaluate_shard/v1";
inline constexpr std::size_t max_layer_states = 1U << 20U;

struct Successor {
    State state;
    std::size_t parent{0};       // index into the batch the worker was handed
    std::size_t op_index{0};     // the operator applied
    std::int64_t step_cost{0};   // that operator's cost
    std::int64_t heuristic{-1};  // the successor's h, or -1 for "unreachable under the relaxation"
    bool preferred{false};       // reached by a preferred operator (h_ff only)

    [[nodiscard]] auto operator==(const Successor&) const -> bool = default;
};

[[nodiscard]] auto encode_task(const Task& task) -> Result<Payload>;
[[nodiscard]] auto decode_task(std::span<const std::byte> bytes) -> Result<Task>;
[[nodiscard]] auto encode_states(std::span<const State> states, Heuristic h) -> Result<Payload>;
[[nodiscard]] auto decode_successors(std::span<const std::byte> bytes)
    -> Result<std::vector<Successor>>;

[[nodiscard]] auto register_ops(TaskRegistry& reg) -> Result<void>;
```

| Type / Constant / Function | Role | Invariant |
| :--- | :--- | :--- |
| `Heuristic` | Selects the evaluation heuristic for worker shards: `h_max` (admissible), `h_add` (inadmissible sum), or `h_ff` (inadmissible relaxed plan with preferred operators). | The admissibility of this choice determines whether the calling search can claim optimality. |
| `expand_op_id` | Operation identifier `"nimblecas.planning.expand_shard/v1"` registered with the `TaskRegistry`. | Applies all applicable operators to a batch of states and evaluates every generated child state. |
| `evaluate_op_id` | Operation identifier `"nimblecas.planning.evaluate_shard/v1"` registered with the `TaskRegistry`. | Evaluates a batch of existing states without generating successors. |
| `max_layer_states` | Upper limit on the number of states a single round graph may materialise ($2^{20} = 1{,}048{,}576$). | Exceeding this limit returns `MathError::overflow`. |
| `Successor` | Record of a single successor state returned by a worker, containing the state, parent batch offset, applied operator index, step cost, heuristic value, and preferred status. | `heuristic == -1` indicates that the state cannot reach the goal under the relaxation. |
| `encode_task` / `decode_task` | Binary serialisation for `Task` structures using the magic constant `0x4e43535f5054534bULL` (`"NCS_PTSK"`). | Validates the task via `nimblecas::planning::validate` prior to encoding and upon decoding. |
| `encode_states` | Binary serialisation for a contiguous slice of `State` vectors and their target heuristic, using magic constant `0x4e43535f50424348ULL` (`"NCS_PBCH"`). | Returns `MathError::domain_error` if `states` is empty. |
| `decode_successors` | Binary deserialisation for worker output payloads, using magic constant `0x4e43535f50535543ULL` (`"NCS_PSUC"`). | Validates buffer bounds before allocating vector capacity. |
| `register_ops` | Registers both `expand_op_id` and `evaluate_op_id` handlers into a `TaskRegistry`. | Must be called on the coordinator and on every remote worker before task dispatch. |

## Graph construction

A single search round partitions a set of candidate states across multiple tasks without
inter-task dependencies.

```cpp
[[nodiscard]] auto build_round_graph(const TaskRegistry& reg, const Task& task,
                                     std::span<const State> states, Heuristic h,
                                     std::size_t shards) -> Result<TaskGraph>;
```

`build_round_graph` constructs a `TaskGraph` containing up to `shards` independent tasks, each
executing `expand_op_id`. States are distributed across shards in contiguous, balanced ranges.
This function is exposed directly so that schedulers, profilers, and batch orchestrators can inspect
or customise round-level DAG execution.

The function returns:
- `MathError::domain_error` if `states.empty()`, if `shards == 0`, or if `task` fails structural
  validation.
- `MathError::overflow` if `states.size() > max_layer_states`.

### Batch evaluation

`distributed_evaluate` evaluates the selected heuristic across an array of states by dispatching
batches across `exec` using `evaluate_op_id`. Each returned element corresponds to the input state
at the same index. An entry of `std::nullopt` indicates that the goal is unreachable from that state
under the delete relaxation; when using `Heuristic::h_max`, this constitutes a proof that the goal
is unreachable in the unrelaxed task.

### Optimal distributed planning (`distributed_astar_plan`)

`distributed_astar_plan` conducts optimal A* search. Because optimality is the defining contract
of this function, the heuristic is not a parameter: it is hardcoded to `h_max`, the only admissible
delete-relaxation heuristic available.

Each search iteration identifies the minimum $f = g + h$ value among open states, extracts every
open state sharing that minimum $f$ into an $f$-layer, and evaluates whether any state in the layer
satisfies the goal condition. If a goal is present, the plan is reconstructed, validated by
`validate_plan`, and returned immediately: no cheaper plan can emerge subsequently, as every
remaining open state has $f \ge f_{\min}$ and $h$ is admissible. If no goal is found, the states of
the layer are partitioned across `shards` and expanded concurrently via `exec`. Successors are
folded into the coordinator's open list in deterministic order (shard index, then batch index, with
ties favouring lower operator indices).

### Satisficing distributed planning (`distributed_gbfs_plan`)

`distributed_gbfs_plan` performs greedy best-first search guided by the `h_ff` heuristic with
preferred operator support. In each round, the coordinator sorts the open list primarily by
heuristic value $h$, secondarily by preferred operator status, and tertiarily by node index.
The best `beam` states are extracted and dispatched across `shards` for concurrent expansion.

The `beam` parameter specifies how many promising states are expanded per round:
- `beam = 1` reproduces serial greedy best-first search.
- `beam > 1` increases the volume of work evaluated per round, reducing total coordinator round trips.

`distributed_gbfs_plan` makes **no claim of optimality** regarding the cost or length of the
returned plan.

## Error model

All fallible operations return `Result<T>` containing either the result or a `MathError`.

| Function | Condition | Error |
| :--- | :--- | :--- |
| Any | Task fails structural validation (`validate`) | `MathError::domain_error` |
| `build_round_graph`, `distributed_astar_plan`, `distributed_gbfs_plan` | `shards == 0` | `MathError::domain_error` |
| `build_round_graph`, `distributed_evaluate` | `states.empty()` | `MathError::domain_error` |
| `distributed_gbfs_plan` | `beam == 0` | `MathError::domain_error` |
| `build_round_graph`, `distributed_astar_plan` | Layer or batch size exceeds `max_layer_states` | `MathError::overflow` |
| `decode_task`, `decode_successors` | Malformed header magic, truncated payload, or inconsistent count | `MathError::syntax_error` |
| `distributed_astar_plan`, `distributed_gbfs_plan` | Expansion count reaches `max_expansions` | `MathError::not_converged` |
| `distributed_astar_plan`, `distributed_gbfs_plan` | Open list exhausted without finding a goal, or initial state has $h = \infty$ | `MathError::undefined_value` |
| `distributed_astar_plan`, `distributed_gbfs_plan` | Generated plan fails validation during `validate_plan` replay | `MathError::domain_error` or `MathError::undefined_value` |

## Worked examples

### Optimal distributed planning across local worker threads

This example constructs a task containing four independent binary switches that must each be toggled
from 0 to 1. The optimal plan cost is exactly 4. Because all switch orderings are equally valid, this
problem exemplifies the equivalence contract: different expansion orderings yield different step
sequences, but `distributed_astar_plan` always returns an optimal cost of 4.

```cpp
import std;
import nimblecas.core;
import nimblecas.planning;
import nimblecas.planning_dist;
import nimblecas.taskdag;

using namespace nimblecas;
using namespace nimblecas::planning;
using namespace nimblecas::planning_dist;

// Build a planning task: 4 independent switches
Task task;
task.domain_size.assign(4, 2); // 4 variables, each with domain {0, 1}
task.initial.assign(4, 0);     // initial state: all switches 0

for (std::size_t i = 0; i < 4; ++i) {
    task.goal.push_back(FactPair{.var = i, .value = 1});
    task.operators.push_back(Operator{
        .name = std::format("flip{}", i),
        .preconditions = {FactPair{.var = i, .value = 0}},
        .effects = {FactPair{.var = i, .value = 1}},
        .cost = 1
    });
}

// Instantiate a multi-threaded parallel executor
auto exec = local_parallel_executor();

// Run distributed A* with 4 parallel worker shards
auto outcome = distributed_astar_plan(task, /*max_expansions=*/200000, /*shards=*/4, *exec);
if (outcome) {
    const PlanResult& res = *outcome;
    // res.plan.cost == 4 (strictly optimal)
    // res.plan.length() == 4
    
    // Every plan is verified by replay from the initial state
    auto replay = validate_plan(task, res.plan);
    // replay.has_value() is true
}
```

### Distributed heuristic batch evaluation

```cpp
import std;
import nimblecas.core;
import nimblecas.planning;
import nimblecas.planning_dist;
import nimblecas.taskdag;

using namespace nimblecas;
using namespace nimblecas::planning;
using namespace nimblecas::planning_dist;

// Create a corridor task: start at 0, navigate to cell 4
Task task;
task.domain_size.push_back(5);
task.initial.push_back(0);
task.goal.push_back(FactPair{.var = 0, .value = 4});
for (std::int32_t i = 0; i < 4; ++i) {
    task.operators.push_back(Operator{
        .name = std::format("step{}", i),
        .preconditions = {FactPair{.var = 0, .value = i}},
        .effects = {FactPair{.var = 0, .value = i + 1}},
        .cost = 1
    });
}

// Sample states: cell 0, cell 2, cell 4
std::vector<State> states = {{0}, {2}, {4}};

auto exec = local_parallel_executor();

// Evaluate h_max across 2 shards concurrently
auto values = distributed_evaluate(task, states, Heuristic::h_max, /*shards=*/2, *exec);
if (values) {
    // (*values)[0] == 4 (distance from 0 to 4)
    // (*values)[1] == 2 (distance from 2 to 4)
    // (*values)[2] == 0 (at goal)
}
```

### Cluster dispatch over `SgeeDistributedExecutor`

When deploying across a cluster using SGEE, both the coordinator and worker processes must
register the planning shard operations into their local `TaskRegistry` instances before running
distributed plans.

```cpp
import nimblecas.core;
import nimblecas.planning;
import nimblecas.planning_dist;
import nimblecas.taskdag;
import nimblecas.taskdag_sgee;

using namespace nimblecas;
using namespace nimblecas::planning;
using namespace nimblecas::planning_dist;

// 1. Initialise the task registry and register the planning operations
TaskRegistry reg;
auto reg_ok = register_ops(reg);

// 2. Configure the distributed executor
SgeeExecutorConfig cfg;
cfg.registry = &reg;
cfg.num_workers = 8;
cfg.poll_interval_ms = 1;

// In testing environments, FakeBrokerPort and InMemoryResultChannel simulate the broker.
// In cluster deployments, real network ports are supplied.
FakeBrokerPort port;
InMemoryResultChannel results;
SgeeDistributedExecutor exec(cfg, port, results);

// 3. Construct a solvable task and run distributed A*
Task task;
task.domain_size = {3};
task.initial = {0};
task.goal = {FactPair{.var = 0, .value = 2}};
task.operators.push_back(Operator{
    .name = "hop",
    .preconditions = {FactPair{.var = 0, .value = 0}},
    .effects = {FactPair{.var = 0, .value = 2}},
    .cost = 1
});

auto result = distributed_astar_plan(task, /*max_expansions=*/10000, /*shards=*/4, exec);
if (result) {
    // The plan produced over SGEE has the identical cost to serial execution
}
```
